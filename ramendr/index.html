How failover works
RamenDR failover is hub-orchestrated: the hub applies a DRPolicy + DRPlacementControl, ACM pushes ManifestWork to the spokes, Ramen promotes the replicated Dell volumes on the secondary, and the VM workloads start there. No spoke-to-spoke pod networking is used - so Submariner is not required.

Why no Submariner here. This is the Dell PowerStore edge track. Dell replicates array-to-array (VSA-A to VSA-B) over the storage network, and RamenDR coordinates failover through the ACM hub plus an S3 metadata store - the two spokes never exchange pod traffic. Submariner (cross-cluster pod networking) is only required for the separate ODF/Ceph AWS track, where the Ceph rbd-mirror pods replicate over the cluster network. Globalnet is also unsupported in ODF Regional-DR, so it is dropped here entirely. RamenDR integration with Dell PowerStore is Tech Preview (Q3 2026); the documented fallback is Dell CSM Replication + ACM + GitOps.

Both spokes are `ocp3m3w-ic4s22` factory clones, so they share the same API hostname and 192.168.129.0/24 subnet - harmless here: the subnets are host-local behind NAT, ACM uses the pull model (spokes dial the hub, keyed by ManagedCluster name), and the clones get distinct clusterIDs. The lab also spans corp 10.46.46.0/24 (hypervisors) and the Dell VSA nets 10.46.48.x (mgmt) + 10.46.49.x (storage). Pod/service CIDRs overlap too (10.128.0.0/14, 172.30.0.0/16) - irrelevant on the Dell path (no cross-cluster pod networking, no Globalnet).

No UDP 4500/4490 (Submariner) forwarding is needed on the Dell path. The edge36 DNATs (6443 + 443) persist via the virtdr-nat systemd service across the hub redeploy. Each spoke host needs a small DNS override so its klusterlet resolves the hub hostname to 10.46.46.12.

Traffic Flows

Management Plane (ACM)

1.Hub API (edge36) exposed on TCP 6443 via nftables DNAT
2.Each spoke host resolves the hub API hostname to 10.46.46.12
3.Each spoke klusterlet dials out to the hub (pull model)
4.ACM manages both spokes and pushes ManifestWork

DR Control Plane (RamenDR)

1.Hub RamenDR operator applies DRPolicy + DRPlacementControl
2.PV/PVC/VRG metadata is stored in the shared S3 store
3.On failover, Ramen promotes the target volumes on the secondary
4.ACM places the VM workloads on the surviving cluster

Storage / Replication Plane

1.Each spoke's Dell CSI talks to its local VSA over iSCSI
2.VSA-A replicates async to VSA-B (Dell native, RPO 15m)
3.Replication runs on the storage network, not the pod network
4.VolumeReplication (VRG) ties the array state to RamenDR
