CSI and CSI-Addons: the DR stack, site by site

How a disaster-recovery request travels from the orchestrator down to a storage array, and which of those pieces run on the hub, on spoke-0 and on spoke-1. The two spokes hold the same software; the boxes show what actually differs.

A specification is a contract, not software

It is a written agreement about which calls exist and what they mean. Kubernetes and a storage product can work together without either team writing custom code, because both sides answer the same calls.

A driver is a translator

The driver is the software that turns those standard calls into commands one storage product understands. One driver per product: PowerStore has one, Ceph has another. Kubernetes picks the driver from the storage class that created the volume.

A sidecar is a helper in the same pod

A pod is the smallest unit Kubernetes runs, and it can hold more than one container. A sidecar is a second container in the driver's own pod that adds a capability, here the newer replication calls, without the driver image having to change.

Three lab words used below. A VSA is one virtual storage array: two virtual machines that act as one appliance. A spoke is one OpenShift cluster and its site. The hub is the central cluster that coordinates the spokes: here it is edge36, with spoke-0 on edge95 and spoke-1 on edge97.

The picture is split by where each piece runs: one box for the hub, one for each spoke, and a strip at the bottom for the comparison stack this lab does not deploy. What runs where, and why the boxes differ

Same request path every time. The site changes what each piece is allowed to do, not the shape of the handoff.

spoke-0 and spoke-1 are peers, not a fixed primary and standby. Both protected applications have spoke-0 as their home site, but which side holds the writable copy at any moment is a fact about one application, taken from the live PlacementDecision. That is why the two spoke boxes show the same software and no permanent role label: after a failover or a Relocate the roles swap, while the boxes stay as drawn.

Follow one request

The same seven handoffs every time a volume is protected, promoted or resynced. Only the first and the last happen on the hub.

1

Ramen decides, on the hub

The hub operator chooses the site and writes the DRPlacementControl. It then delivers one VolumeReplicationGroup to each spoke. It does not call any storage system.

2

The site's Ramen writes the volume request

On the spoke, the cluster operator reads its VRG and creates a VolumeReplication or VolumeGroupReplication in the application's namespace.

3

The site's controller picks the driver

The csi-addons controller on that spoke sees the new object, reads which volume it names, and works out which storage driver owns that volume.

4

It finds that driver's sidecar

Each sidecar publishes a CSIAddonsNode record, so the controller knows how to reach it and which operations the driver supports.

5

The sidecar forwards the call

The controller sends one gRPC call, a fast remote procedure call of the same kind the CSI standard uses. The sidecar passes it to its own driver over the driver's local socket, inside the same pod.

6

The driver talks to the local array

For PowerStore: enable replication, promote the copy, demote the old side, or resync. The controller pod uses the array's REST API and the worker pods carry the data over NVMe/TCP. The array does the actual copying on its own schedule.

7

The answer goes back up

The controller writes the result into the object's status. The spoke VRG reports it, and the hub operator reads that report and decides the next step of the recovery.
